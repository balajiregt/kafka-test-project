# Universal Event Assurance Framework

The assurance layer is designed to be reused outside the sample account application. The account APIs are only a reference producer of events.

Reusable pieces:

- `com.balaji.kafkaeventlab.assurance`
- `GET /api/assurance/subjects/{subjectId}/journey`
- `GET /api/assurance/subjects/{subjectId}/findings`
- `GET /api/assurance/testing-recommendations`
- `app.assurance` configuration in `application.yml`
- `EventEvidenceSource` for plugging in different evidence backends
- `/assurance-report.html?subjectId={subjectId}`

## What A Team Configures

The framework should not know business lifecycle rules in Java. A team cloning this project should configure:

- Required event metadata fields.
- Event ordering rules.
- Event flag rules.
- Graph relationship mappings.
- Testing recommendations.

Example:

```yaml
app:
  assurance:
    evidence:
      source-type: jpa

    metadata-rule:
      rule-id: metadata.required-fields
      required-fields:
        - eventType
        - aggregateId
        - subjectId
        - correlationId
        - schemaVersion
        - offsetNumber

    ordering-rules:
      - rule-id: order.payment-before-shipment
        trigger-event-type: ORDER_SHIPPED
        required-prior-event-type: PAYMENT_CAPTURED
        status-on-failure: FAIL
        severity-on-failure: HIGH
        recommended-test-layer: Kafka integration

    event-flag-rules:
      - rule-id: fraud.events-reviewed
        event-type: FRAUD_REVIEW_REQUIRED
        status-when-present: WARN
        recommended-test-layer: API integration

    graph-edge-rules:
      - when-aggregate-type: PAYMENT
        edge-type: PAYS_FOR
        label: "{eventType}"
```

## What Stays Generic

The advisor does not hardcode event names such as registration, sign-in, payment, shipment, or reset. It evaluates configured rules against ordered event evidence.

The graph service always creates framework edges:

- `PRODUCED_EVENT`
- `AFFECTS_SUBJECT`
- `FOLLOWS_EVENT`

Domain-specific edges come from `app.assurance.graph-edge-rules`.

## Evidence Sources

The assurance engine reads normalized event evidence through this interface:

```java
public interface EventEvidenceSource {
    List<EventEvidence> findBySubjectId(UUID subjectId);
}
```

The default source is `JpaEventEvidenceSource`, enabled by:

```yaml
app:
  assurance:
    evidence:
      source-type: jpa
```

That default works well for local development, H2, Postgres, and CI evidence stores. Bigger projects can add another implementation without changing the advisor, graph, report, or rule engine.

Possible enterprise implementations:

- `KafkaReplayEventEvidenceSource`: replay events from a topic by key, timestamp, or correlation id.
- `OpenSearchEventEvidenceSource`: read indexed event logs from a test environment.
- `LokiEventEvidenceSource`: parse structured logs from Kubernetes pods.
- `DatadogTraceEvidenceSource`: resolve evidence from trace/span tags.
- `CiArtifactEvidenceSource`: read normalized event JSON generated by a pipeline job.

## Kubernetes / Orchestration Usage

In a larger environment, the flow should look like this:

```text
deploy app to test namespace
run API or message-driven scenario
collect event evidence from Kafka, logs, DB, or observability store
normalize into EventEvidence
run assurance graph and advisor
publish report as CI artifact
fail pipeline on configured FAIL findings
```

The important boundary is:

```text
orchestration-specific collection -> EventEvidenceSource -> generic assurance engine
```

Kubernetes, Helm, ArgoCD, Jenkins, GitHub Actions, or any other orchestration tool should only affect how evidence is collected. It should not affect how lifecycle rules are evaluated.

## Does The Current Setup Fit Big Orchestrations?

Yes for the assurance core, with one important distinction.

The current H2/JPA setup is a local evidence store. It is useful for developer laptops, Testcontainers, and CI jobs that want a simple database-backed report. It is not pretending to replace Kubernetes, service mesh, platform logs, managed Kafka, schema registry, or observability tooling.

The scalable part is the contract between orchestration and assurance:

```text
environment-specific collector -> normalized EventEvidence -> graph/advisor/report
```

That means a large project can keep its real deployment style:

- deploy services with Helm, ArgoCD, Jenkins, GitHub Actions, or another platform pipeline
- run tests against a Kubernetes namespace or ephemeral test environment
- collect events from Kafka, logs, traces, audit stores, or CI artifacts
- normalize those records into `EventEvidence`
- run the same graph and advisor rules

For this repository, the built-in implementation is `JpaEventEvidenceSource`. For a large platform, the next implementation would usually be one of:

- `KafkaReplayEventEvidenceSource`: seek/replay topic records for a subject id or correlation id.
- `OpenSearchEventEvidenceSource`: read indexed event logs from a shared test environment.
- `LokiEventEvidenceSource`: query structured pod logs from Kubernetes.
- `DatadogTraceEvidenceSource`: collect events from trace/span metadata.
- `CiArtifactEvidenceSource`: read normalized JSON produced by pipeline steps.

So the answer is: the current sample setup is intentionally lightweight, but the framework shape can accommodate bigger orchestration because the orchestration-specific work is isolated behind `EventEvidenceSource`.

## AI Assistant Context Inputs

The BYOK AI assistant helps users draft `app.assurance` YAML, and it is restricted to assurance-configuration help. It should ask for or accept these context inputs:

- AsyncAPI, event catalog, or schema registry exports for Kafka event contracts.
- OpenAPI or Swagger for command APIs and business operations.
- Sample event payloads from lower environments.
- Consumer ownership and topic ownership documentation.
- Business workflow or lifecycle diagrams.
- Existing test-layer strategy, including what belongs in API, Kafka, contract, and UI/e2e tests.
- Known failure policies such as retry, DLQ, idempotency, duplicate handling, and ordering expectations.

OpenAPI/Swagger alone is not enough for Kafka assurance. It helps infer commands and business operations, but AsyncAPI, event schemas, topic details, sample payloads, and consumer expectations are stronger inputs for Kafka rules.

The assistant should refuse unrelated requests and produce only framework artifacts such as YAML rules, metadata expectations, graph edge mappings, test recommendations, and review comments on supplied assurance configuration.

## Assurance Config Assistant

The project includes a scoped assistant endpoint:

```text
POST /api/assurance/config-assistant
```

It has two modes:

- `local-template`: deterministic starter YAML when no API key/model is supplied.
- `byok-ai`: request-scoped live AI call when the user supplies an API key and model, or when the configured environment variable contains the key.

The API key is not stored by the app. It is used only for the current request.

Example request:

```json
{
  "message": "Create assurance YAML for these Kafka events and classify the test layers.",
  "contextSources": [
    {
      "sourceType": "asyncapi",
      "name": "order-events",
      "content": "ORDER_CREATED, PAYMENT_CAPTURED, ORDER_SHIPPED events with correlationId and schemaVersion"
    }
  ]
}
```

The assistant applies guardrails before it calls any live model. It only accepts assurance-related requests and supported context types. Unrelated prompts return `REFUSED`.

Supported context types are configured under:

```yaml
app:
  assurance:
    assistant:
      allowed-context-types:
        - asyncapi
        - openapi
        - swagger
        - event-catalog
        - schema
        - sample-payload
        - workflow
        - test-strategy
        - consumer-ownership
        - freeform
```

## How To Use In Another Project

1. Keep or copy the `assurance` package.
2. Feed consumed events into an evidence source with event id, event type, aggregate id, subject id, correlation id, topic, partition, offset, timestamps, schema version, and payload JSON.
3. Configure `app.assurance` for your event model.
4. Run API/Kafka tests locally or in CI.
5. Open the report with `/assurance-report.html?subjectId={id}`.

The sample account application can be deleted or replaced once another project provides its own event producer, consumer, and EventEvidenceSource implementation.
